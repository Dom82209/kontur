Дата фиксации: 27 октября 2026 года.

Этот документ фиксирует порядок изменений и границы контрактов до реализации. Этапы выполняются последовательно; следующий этап не начинается при красных проверках предыдущего.

## Архитектурное решение workspace

Учебные сущности изолируются отдельной SQLite на workspace. Глобальная база-каталог хранит только identity, тип, fingerprint, относительный путь к workspace SQLite, активный выбор и журнал переходов. Это делает невозможным SQL-запрос, случайно смешивающий предметы, ДЗ, AI jobs, packages или receipts двух vault.

Путь vault нельзя заменить у активного workspace. Новый vault создаёт новый identity; ранее зарегистрированный vault подключается только после совпадения marker/fingerprint. Preview перехода не пишет в vault или workspace SQLite. Apply требует отдельного подтверждения и повторной валидации.

## Этап 2: подключение существующего vault

Состав:

- `file_service/scan.rs` — read-only fd-relative обход vault (`O_NOFOLLOW`; скрытые записи не открываются; symlink, спецфайлы и имена не в UTF-8 попадают только в отчёт; лимиты 50 000 записей / глубина 12) и потоковый SHA-256.
- `adoption.rs` + миграция v11 — неизменяемый план `vault_adoption_plans` (preview → apply / dry-run / cancel, TTL 30 мин, SHA-256 плана, триггеры неизменяемости), стабильные id из identity пространства и относительного пути (идемпотентность), повторное хэширование каждого нового файла перед apply, одна транзакция, provenance в `vault_adoption_items`. Изменённые после импорта файлы и конфликты с базой не применяются, а показываются.
- Классификация: папка недели задаёт категорию; внутри `03 ДЗ` — данные (имя), своя работа (фамилия из настроек, кириллица и латиница; версии `_v01`; `.tex`; решение/черновик), условие (LMS-хэш-суффикс `_xxxxxxxx`; PDF с «ДЗ»). Неуверенные случаи (< 0.7) помечены «проверьте категорию»; ручная категория имеет приоритет, категории ДЗ доступны только файлам из `03 ДЗ`.
- Неизвестные сроки ДЗ и даты недель хранятся честно (`deadline = NULL`, даты `''`; DTO — `Option`/`null`), UI пишет «срок не указан» / «даты недели не заданы» (часть этапа 5, перенесена раньше).
- Tauri-команды `preview_vault_adoption`, `apply_vault_adoption(planId, overrides, dryRun)`, `cancel_vault_adoption`; apply берёт общий замок файловых мутаций. UI: «Настройки → Управляемые каталоги → Подключить материалы…».

Проверка на настоящем vault (только чтение): из Obsidian взят лишь список путей (570 файлов, без содержимого); зеркало структуры с файлами-заглушками прогнано через preview и dry-run (`adoption::tests::mirror_of_real_vault_preview`, `#[ignore]`, путь списка в `KONTUR_MIRROR_PATHS`). Итог: 11 предметов, 43 недели, 39 ДЗ, 291 файл к подключению; пропущено 279 (139 заметок Obsidian, 136 файлов `00 Общие материалы`, 3 файла `Неделя 00`, 1 служебная папка); 63 файла с неуверенной категорией; dry-run прошёл без ошибок. Apply на настоящем vault не выполнялся.

## Этап 3: предметы

- Схема v12: `subjects.archived_at`, `merged_into_id`, `revision`; таблица `subject_keywords` (ключевые слова перенесены из JSON настроек, `AutomationRules.subjectRules` теперь производное от неё); журнал `subject_merges` (append-only). Триггеры: слитый предмет всегда в архиве, слияние необратимо, слияние с самим собой запрещено.
- `SubjectService` / команды `create_subject`, `update_subject`, `set_subject_archived`, `preview_subject_merge`, `merge_subjects`. Ни одна не пишет в vault: папка `Предметы/<название>` задаётся при создании и не меняется при переименовании. Имена и папки уникальны без учёта регистра (как в APFS). Изменения — с optimistic revision.
- Ключевое слово не может принадлежать двум активным предметам (иначе классификация стала бы неоднозначной); возврат из архива проверяет это заново.
- Слияние: предпросмотр ничего не пишет; применение только при совпадении fingerprint. Недели переходят к целевому предмету вместе со своими папками, ключевые слова и классификации «Входящих» — тоже; ручные решения остаются ручными. Недели с одинаковыми номерами у обоих предметов блокируют слияние.
- Классификация «Входящих» теперь использует тот же классификатор, что и экспорт ЦУ: ключевые слова предметов и порог `lowConfidenceThreshold` из настроек (раньше порог был зашит как 0.7). Архивные предметы не предлагаются; ручной выбор архивного предмета и раскладка в него блокируются. Существующая неделя раскладывается в свою папку.
- UI: «Настройки → Предметы»; архивные предметы скрыты из навигации, палитры команд и списков выбора.

## Этап 4: несколько ДЗ в неделе

- Схема v13: `homeworks.week_id` больше не уникален; уникальны `(week_id, ordinal)`; `import_key` — стабильная внешняя идентичность (для ДЗ из vault — `vault:<папка>`). Неделя, ordinal и заданный import_key неизменяемы (триггер). Все прежние ДЗ получили `ordinal = 1`.
- Перестройка таблицы, на которую ссылаются 13 других, идёт по 12-шаговой процедуре SQLite: раннер миграций выключает внешние ключи только для такой миграции, переименовывает с `legacy_alter_table`, требует пустой `foreign_key_check` до коммита и восстанавливает настройки при любом исходе. Без этого `DROP TABLE` каскадно удалил бы файлы, проверки, комментарии и снимки. Тест обновления v12→v13 подтверждает отсутствие потерь и работу триггеров сданного ДЗ.
- Новое ДЗ недели (`create_homework`) создаётся только в базе: следующий ordinal, папка `03 ДЗ (N)`, срок — дата с часовым поясом (хранится в UTC) или «не указан».
- Раскладка: одно ДЗ в неделе — файл идёт в него; ни одного — создаётся первое и файл к нему привязывается (раньше файл оставался без `homework_id`); несколько — нужен явный выбор (в назначении или в ручной классификации файла, `homeworkId`). Лекции и семинары привязываются к неделе, не к ДЗ. Карточка ДЗ пишется в папку своего ДЗ, обзор недели ссылается на все ДЗ.
- Подключение vault: ДЗ недели в другой папке больше не конфликт — папка vault становится следующим ДЗ недели.

## Этап 5: семестр и сроки

- Схема v14: одна запись `semester_settings` (местная дата начала недели 1, смещение от UTC с шагом 15 минут, 1–60 недель, ревизия); `weeks.dates_source` (`unknown` / `semester` / `legacy`); `homeworks.deadline_source` (`manual` / `lms`; пусто при наличии срока = `legacy`).
- Неделя N начинается в 00:00 местного времени `start + 7·(N−1)` дней и длится 7 дней минус секунда; хранится UTC (RFC 3339). Тесты: Москва, западное смещение, граница года (неделя 18: 29.12.2026–04.01.2027), моменты до начала и после конца семестра.
- Сохранение семестра (с optimistic revision) пересчитывает даты всех недель. Новые недели (раскладка, создание недели, подключение vault) берут даты из семестра, без него — «неизвестны». Даты, записанные до этапа 5 «от сегодня», показываются как приблизительные.
- Главная: номер учебной недели — только из семестра; без семестра или вне его — «семестр не настроен» вместо недели ~2900 от 1970 года.
- Сроки: раскладка больше не ставит условный срок «+7 дней» — новое ДЗ получает срок «не указан». `set_homework_deadline` задаёт точный срок (RFC 3339 с поясом → UTC) или очищает его; у сданного ДЗ срок неизменяем. Старые сроки помечаются «приблизительный, уточните».
- UI: «Настройки → Семестр», «Указать/Изменить срок» на странице ДЗ, пометки у недель.

## Этап 6: автоматизация

Аудит настроек показал, что из 15 полей backend исполнял только ключевые слова, порог неуверенности, фамилию (подключение vault) и инварианты подтверждений. Остальное сохранялось, но ни на что не влияло.

- Удалены из контракта (`AutomationRules` в Rust и TypeScript): `downloadsWatchPath`, `obsidianVaultPath` (их задают «Управляемые каталоги»), `semesterStart`, `weekDetection` (их заменил семестр этапа 5), `versionPattern` (файлы версий не переименовываются), `backupBeforeChange` (резервные копии не создавались: файлы не перезаписываются), `autoRouteHighConfidence` (автораскладки нет — раскладка всегда по нажатию). Сохранённый JSON со старыми полями читается: они отбрасываются при загрузке.
- `inboxPath`, `confirm.*` — производные/инварианты: значения из JSON игнорируются при чтении, попытка сохранить другие — ошибка без частичных изменений. Переключатели подтверждений на странице «Автоматизация» заменены описанием встроенных гарантий.
- `finalNamePattern` теперь исполняется: сборка комплекта называет файл в «03 На сдачу» по шаблону (`naming.rs`), раньше — `Итог_<id>`. Шаблон проверяется при сохранении (известные токены, обязательный `{Неделя}`, без `/ \ :`), значения токенов очищаются от разделителей пути; если шаблон использует незаданные фамилию/имя, сборка блокируется с подсказкой. Те же правила во frontend (`validateNamePattern`) — для предупреждения до сохранения.
- Неделя: номер из пути важнее всего; без номера и при настроенном семестре предлагается неделя по дате загрузки — с низким весом и всегда со статусом «неоднозначно».
- Сохранение правил не отменяется через журнал ни в backend, ни в mock (раньше mock обещал «Отменить» и «резервную копию»). Черновик правил следует за сохранёнными значениями, пока нет несохранённых правок.
- Тесты: перезапуск (файловая SQLite закрыта и открыта заново), чтение legacy JSON, инварианты без частичных изменений, имя комплекта по шаблону и блокировка без фамилии, порог меняет статус, неделя по дате загрузки; mock повторяет контракт.

## Этап 7: авторитетность и устаревание

- Схема v15: `teacher_comments.authority` (`teacher_official`, `teaching_assistant`, `student`, `group_chat_unverified`, `user_note`, `system`, `unknown`), `author`, `context` (ссылка/цитата), `official_confirmed_at`; журнал `comment_authority_events` (только добавление); `teacher_requirements.withdrawn_at`; `inputs_fingerprint` у `review_runs`, `revision_prompts`, `submission_packages`; `homeworks.ready_fingerprint`.
- Официальный ответ = преподаватель или ассистент + явное подтверждение пользователя. Мнение студента, сообщение общего чата, заметка, системный текст и ответ неизвестного автора не могут стать официальными (сервис и триггер). Требование создаётся только из официального ответа. Импорт переписки сохраняет ответы как неофициальные. Существующие до v15 ответы получили `unknown`.
- Отпечаток (`workflow/fingerprint.rs`) вычисляется из SQLite при каждом чтении: материалы недели/ДЗ, условие и ссылка на задание, выбранная версия и её состав, явно выбранный профиль стиля, официальные ответы и действующие требования. Проверка, промт и комплект запоминают его при создании; при несовпадении они `stale`. Записи до v15 (`NULL`) считаются устаревшими.
- Готовность требует проверку текущей версии по актуальному отпечатку (`inputs_fresh`). «Готово к сдаче» запоминает отпечаток; добавление/подтверждение/отзыв официального ответа, новое или отозванное требование, требование «не выполнено» снимают отметку в той же транзакции; изменения материалов, условия или профиля делают её недействующей (`readyStale`), пока работу не проверят заново. Устаревший промт нельзя передать автору (правка черновика обновляет отпечаток). Отзыв официальности и удаление ответа отзывают его требования; отозванные хранятся для истории и неизменяемы.
- Команды `set_comment_authority`, `withdraw_teacher_requirement`; UI: «Кто ответил», имя, ссылка/контекст, подтверждение официальности; отметки «Официально / Не официально», «Отозвано»; предупреждения об устаревших готовности, промте и комплекте.

## Этап 8: комплект V2

- Схема v16: `submission_packages` перестроена с выключенными внешними ключами (как v13): снят `UNIQUE(homework_id)`, добавлены `revision` (строго по порядку), `requirements_json`, `inputs_json`. Прежний комплект становится ревизией 1 (устаревшей: нет отпечатка). Триггеры: содержимое ревизии неизменяемо, статус меняется только на `submitted` и один раз, удалять ревизии нельзя. Ручные отметки — журнал `package_manual_checks` (только `links` и `manual_review`, только добавление, у отправленной ревизии — запрещены).
- Сборка (`build_submission_package`): только на этапе «Готово к сдаче» с действующей отметкой и пройденной готовностью; каждая сборка — новая ревизия в «03 На сдачу/Ревизия NN»; файлы копируются с проверкой SHA-256; в ревизии — итоговое имя, приложения, ссылки, действующие требования, SHA-256, размеры, относительные пути, время, отпечатки входных данных, пункты с подробностями и предупреждения. Отпечаток сверяется повторно в транзакции записи.
- Статусы: `verified`, `missing`, `stale`, `manual_required`, `inaccessible`, `mismatch`, `not_applicable`. Ссылка всегда `manual_required` (сетевой проверки нет), пока пользователь не подтвердит пункт. Требование «не выполнено» — `missing`, «ручная проверка» — `manual_required` без возможности отметить в комплекте.
- `verify_submission_package` проверяет файлы действующей ревизии на диске (существование, размер, SHA-256) — запись в JSON сама по себе ничего не доказывает.
- Подтверждение отправки: только текущая ревизия по актуальным данным; повторная проверка готовности и файлов; блокируют `missing`, `stale`, `mismatch`, `inaccessible`, неподтверждённые ручные пункты. В транзакции квитанции ещё раз сверяются этап, последняя ревизия и отпечаток. Снимок неизменяем, содержит manifest с SHA-256; на сайт вуза ничего не отправляется.
- UI: номер ревизии, статусы файлов/ссылок/пунктов, «Проверить файлы на диске», история ревизий; кнопка «Отменить» после сборки убрана (ревизии не удаляются).

## Этап 9: профиль личного стиля

- Схема v17: `style_sources` (явно выбранные файлы внутри хранилища; исключение — `removed_at`, без удаления; прежние `style_profile_sources` перенесены), `style_profile_revisions` (неизменяемые, по порядку, без удаления: отпечаток источников, снимок источников, признаки, ограничения, статус `ready`/`insufficient_sources`/`unsupported`, причины), `style_checks` (неизменяемые: статус, оценка только при `checked`, порог, фрагменты, признаки, ссылки на образцы, ревизия профиля, отпечаток версии и входных данных), `style_check_confirmations`.
- Никакого сканирования папок: `add_style_source` принимает только путь внутри хранилища и читает только этот файл. Сеть не используется.
- Признаки (`style/features.rs`): длина предложений (среднее, медиана, p90), длина абзацев, формальность, вводные, связки, частотные слова, начала предложений и концовки абзацев, заголовки и списки, пунктуация, категоричность и смягчения, клише; до 3 коротких примеров (≤160 символов) на источник. Копии работ не хранятся. Markdown-описание стиля даёт только правила (пункты списков).
- Профиль пригоден при ≥300 словах подтверждённых работ на выбранном языке. Новая ревизия — только при изменении набора/содержимого источников или языка; «Проверить источники» перечитывает файлы и делает профиль устаревшим при изменениях.
- Проверка версии: по устаревшему профилю — `not_checked`; без профиля/с непригодным — `insufficient_sources`/`unsupported`; формат без текста (xlsx, скан PDF, <60 слов) — `manual_required`; иначе `checked` с эвристическим расхождением 0..10 и порогом из настроек. Готовность (`style`) требует действующей проверки: оценка в пределах порога либо явное ручное подтверждение. Оценка из AI-проверки больше не засчитывается.
- Отпечаток этапа 7 включает последнюю ревизию профиля и состояние источников: их изменение делает устаревшими проверки стиля, проверки версии, готовность, промты и комплекты.
- Терминология UI: «соответствие личному стилю», «нехарактерный фрагмент», «эвристическая оценка», «требуется ручная проверка»; явное пояснение, что низкое соответствие не доказывает использование ИИ.

## Известные ограничения

- Файлы `00 Общие материалы` и `Неделя 00` не подключаются: схема требует неделю с номером ≥ 1. Они перечислены в отчёте с причиной.
- Изменённые после подключения файлы не обновляются планом (статус `changed`); обновление версий — этап 10.
- Отпечаток материалов строится по метаданным SQLite (`content_hash`, размер, статус файлов); изменение файла на диске без пересканирования отражает только проверка свежести источников (`sources_fresh`).
- Доступность внешних ссылок «Контур» не проверяет по сети: только ручное подтверждение.
- Сроки и даты недель после подключения неизвестны до настройки семестра (этап 5).
- Переименование предмета не переименовывает папку в vault; слияние не перемещает файлы — недели сохраняют папки исходного предмета.

- Legacy real-пространство (schema ≤ 8) без marker опознаётся по canonical path + dev/inode. Перенос такого vault на другой Mac или восстановление из копии меняет inode, и «Подключить существующее» будет заблокировано. Явное действие «записать marker в legacy vault» пока не реализовано (подключение материалов его не требует); вынесено в этап 13.
- Проверки `cargo test` в Linux-окружении: 20 тестов `ai::*` требуют macOS `sandbox-exec`; окончательный прогон — на Mac (`logs/run-checks.command`, логи в `logs/`).

## Ограничения до финального GO

- Настоящий Obsidian допускается только для read-only preview; apply/import запрещён до production-аудита.
- Все filesystem-тесты используют `TempDir` или отдельную синтетическую копию.
- Codex/Claude не получают настоящий запрос во время тестов.
- Readiness, package и submitted snapshot не считаются основанием для реальной сдачи, пока P0/P1 из аудита не закрыты.

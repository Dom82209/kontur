# Безопасность файлового сервиса

Diagnostic export этапа 13 не обходит vault и не читает учебные файлы. Место сохранения выбирает сам пользователь в native save dialog; запись по symlink блокируется. Абсолютные пути, имена и содержимое документов в JSON не попадают.

## Внешние AI CLI (этап 9.2)

File service не выдаёт CLI пути учебных файлов. Текст извлекается локально и передаётся через stdin. Отдельный `IsolationRunner` разрешает внешнему процессу только системный runtime, проверенный executable, минимальный auth resource и уникальный job-каталог `0700`; остальные файлы пользователя закрыты deny-by-default Seatbelt-профилем. Полная модель угроз, self-test и ограничения `sandbox-exec` описаны в `docs/AI_ISOLATION_SECURITY.md`.

Статус: этап 9 (процессы официальных CLI — раздел этапа 9); этап 7 — fd-relative фундамент подключён к импорту во «Входящие» (`src-tauri/src/intake/`), к watcher загрузок и импорту экспорта ЦУ (`src-tauri/src/lms/`) и к локальному извлечению текста (`src-tauri/src/extraction/`, только чтение). Прямого IPC к file service нет; при старте приложение файлов не трогает (watcher стартует, только если пользователь его включил, и только читает). Все filesystem-тесты используют только `tempfile::TempDir`.

## Модель угроз

Атакующий — любой локальный процесс того же пользователя, который во время операции может переименовывать, удалять и создавать файлы, каталоги и symlink внутри vault, inbox, backup и рядом с source. Цель атаки — заставить «Контур» записать, перезаписать, прочитать как доверенный или удалить файл за пределами контролируемого корня, либо удалить чужой файл внутри корня.

Строковые проверки пути (`canonicalize`, `starts_with`, `symlink_metadata`) с последующей операцией по абсолютному пути не защищают от этого: между проверкой и `open`/`rename`/`unlink` родительский каталог можно заменить symlink (TOCTOU). Поэтому после этапа 4D.1.1 строковый путь разрешается только один раз — при открытии корня или source.

## Trust boundaries

- `VaultRoot`, `BackupRoot` — абсолютный существующий каталог, не `/`, не домашний и не широкий системный (`/x`). Политика проверяется по canonical path, затем корень **один раз** открывается `open(O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)`. Дальше корень представлен только открытым directory fd (`Arc<OwnedFd>`). Значение AutomationRules `"."` по-прежнему отклоняется.
- `InboxRoot` — не путь, а fd, полученный покомпонентным обходом от fd vault. Symlink или не-каталог в любом компоненте отклоняется.
- `SourceFile` — недоверенный абсолютный путь из native intake. Он открывается **один раз** `open(O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_NOCTTY | O_CLOEXEC)`; symlink в последнем компоненте даёт `ELOOP` → `blocked`. Тип проверяется `fstat` открытого fd: каталог, FIFO, socket и устройства отклоняются. `O_NONBLOCK` исключает зависание на FIFO до проверки типа. Путь не сериализуется и не сохраняется.
- `PersistentPath` — единственная сериализуемая форма учебного пути: относительная, `/`-разделители, без `..`, `.`, пустых компонентов, `file://`, backslash, абсолютного или Windows drive prefix.
- `VerifiedDestination` связывает открытый root и `PersistentPath`. Абсолютный `PathBuf` наружу не выдаётся; метода получения абсолютного пути больше нет.

## fd-relative обход

`fd::walk_parent` открывает каждый промежуточный компонент отдельно:

```text
current = root_fd
for name in components[..last]:
    current = openat(current, name, O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)
```

- Symlink в любом компоненте отклоняется ядром (`ELOOP`); regular file — `ENOTDIR`. Оба дают `blocked`.
- При создании отсутствующий компонент создаётся `mkdirat(current, name, 0755)`, затем снова открывается `openat(... O_NOFOLLOW)`. Если конкурент успел положить на это имя symlink, повторное открытие отклоняется; `EEXIST` от гонки двух `mkdirat` безопасен.
- Результат — fd родительского каталога. Все дальнейшие операции идут через него, поэтому последующая подмена любого компонента пути не перенаправляет операцию: fd продолжает указывать на исходный inode каталога.

### Контроль подмены родителя

Fd защищает от записи «не туда», но после подмены относительный путь в receipt мог бы перестать указывать на созданный файл. Поэтому `fd::verify_parent_identity` повторно обходит путь от root fd без создания и сравнивает `(st_dev, st_ino)` полученного каталога с уже открытым fd родителя. Несовпадение, symlink или исчезновение каталога дают `blocked` («Целевая папка была подменена во время операции»).

## Используемые системные вызовы

| Действие | Вызов |
|---|---|
| Открытие корня | `open(O_RDONLY \| O_DIRECTORY \| O_NOFOLLOW \| O_CLOEXEC)` |
| Обход каталога | `openat(dir_fd, name, O_RDONLY \| O_DIRECTORY \| O_NOFOLLOW \| O_CLOEXEC)` |
| Создание каталога | `mkdirat(dir_fd, name, 0755)` + повторный `openat` с `O_NOFOLLOW` |
| Проверка имени | `statat(dir_fd, name, AT_SYMLINK_NOFOLLOW)` |
| Чтение существующего файла | `openat(dir_fd, name, O_RDONLY \| O_NOFOLLOW \| O_NONBLOCK \| O_NOCTTY \| O_CLOEXEC)` + `fstat` |
| Создание temp | `openat(dir_fd, ".kontur-<uuid>.tmp", O_RDWR \| O_CREAT \| O_EXCL \| O_NOFOLLOW \| O_CLOEXEC, 0644)` |
| Публикация | `renameat_with(dir_fd, temp, dir_fd, final, RENAME_NOREPLACE)`; на macOS rustix отображает флаг в `renameatx_np(RENAME_EXCL)` |
| Cleanup | `statat(dir_fd, name, AT_SYMLINK_NOFOLLOW)` + сравнение identity + `unlinkat(dir_fd, name, 0)` |
| Синхронизация | `fsync(temp_fd)`, `fsync(dir_fd)` |
| Чтение для SHA-256 | `pread` (`FileExt::read_at`) по открытому fd |

Все создаваемые fd имеют `CLOEXEC`. Мутации внутри корней не выполняются через абсолютные строковые пути. Path-based вызовы остались только там, где путь ещё не привязан к fd: проверка политики корня с его однократным открытием и однократное открытие source.

## Source: один inode

`SourceFile` хранит открытый `File` и identity `(st_dev, st_ino)`. `revalidate()` делает `fstat` того же fd и требует regular file с той же identity. Хэш (`hash_source`), размер и копирование читают **один открытый inode** через `pread` от смещения 0. Копирование выполняется одним проходом: каждые скопированные байты одновременно хэшируются, поэтому receipt SHA-256 описывает именно записанное содержимое. Размер `fstat` до копирования, после копирования и число скопированных байт обязаны совпасть. Подмена пути source после открытия не влияет на операцию (`source_is_bound_to_the_inode_opened_once`).

## SHA-256 и планирование

SHA-256 вычисляется блоками по 64 KiB через `pread` и возвращается lowercase hex; файл целиком в память не загружается.

`plan_copy` read-only:

1. `fstat` source;
2. fd-relative обход существующих родителей без создания; отсутствующий родитель → `Copy`;
3. `openat(... O_NOFOLLOW)` конечного имени: нет файла → `Copy`; symlink/каталог/специальный файл → `blocked`;
4. сравнение SHA-256 открытого source и открытого destination: совпало → `SameContent` (копия не создаётся);
5. иначе `NameConflict { suggestedName }`: имена `Файл (2).pdf`, `Файл (3).pdf`… проверяются `statat` в том же fd каталога; расширение и кириллица сохраняются, длина ограничена;
6. перед возвратом решения — `verify_parent_identity`. Подмена родителя во время planning даёт `blocked`, а содержимое за пределами корня никогда не читается как destination.

Planner не создаёт каталогов и файлов.

## Atomic copy

1. `fstat` source, запоминается размер.
2. `ensure_parent`: fd-relative обход с `mkdirat`.
3. `verify_parent_identity`, проверка отсутствия final через `statat`.
4. `openat(O_CREAT | O_EXCL | O_NOFOLLOW)` temp в fd родителя; запоминается identity temp. Создаётся guard.
5. Однопроходное копирование + SHA-256, `fsync(temp)`, сверка размера, сверка с ожидаемым хэшем (если задан), повторный хэш temp через тот же fd.
6. `verify_parent_identity`, повторная проверка отсутствия final.
7. `renameat_with(..., RENAME_NOREPLACE)` внутри одного dir fd. Конкурентно появившийся final даёт `conflict`; overwrite невозможен.
8. `verify_parent_identity`; `statat(final, AT_SYMLINK_NOFOLLOW)` обязан вернуть regular file с identity temp и ожидаемым размером; повторный хэш через fd созданного inode.
9. `fsync(dir_fd)`; guard подтверждается.

### Guards и cleanup

`TempGuard` и `FinalGuard` хранят `Arc` fd подтверждённого каталога, имя и identity созданного inode. При ошибке они **не** разрешают абсолютный путь: выполняется `statat(dir_fd, name, AT_SYMLINK_NOFOLLOW)`, и `unlinkat(dir_fd, name, 0)` вызывается только если имя всё ещё указывает на regular file с той же `(st_dev, st_ino)`. Если конкурент заменил temp другим файлом, чужой файл не удаляется (`cleanup_only_removes_inode_created_by_this_operation`). Если каталог был заменён symlink, удаление происходит в исходном inode каталога, а файл с тем же именем снаружи не трогается.

Остаточное окно: POSIX не даёт атомарного «unlink, если inode совпадает». Между `statat` и `unlinkat` процесс с правами записи в тот же подтверждённый каталог может переименовать другой файл на это же имя. Такой процесс и так может удалить этот файл сам; выйти за пределы каталога через это окно нельзя.

## Backup

`create_backup` открывает оригинал fd-relative внутри vault (`SourceFile::open_in`: обход без symlink, `openat(O_NOFOLLOW)`, проверка identity родителя), строит путь `<operationId>/<relative>` в `BackupRoot`, выполняет `plan_copy` (существующий backup → `conflict`), считает SHA-256 открытого inode и копирует через `atomic_copy_expected`. Изменение содержимого между хэшем и копированием отклоняется. `BackupManifest` в camelCase содержит только operation ID, относительные source/backup paths, SHA-256, размер и UTC creation time.

## Undo foundation

`UndoManifest` в camelCase содержит operation ID, созданные файлы с ожидаемыми SHA-256 и backup entries с относительными original/backup paths и ожидаемым backup SHA-256.

`validate_undo` требует `undoable`, отклоняет уже отменённую операцию и submitted Homework. Для каждого файла: fd-relative обход родителей (symlink в промежуточном компоненте → `blocked`), `openat(O_NOFOLLOW)` конечного имени (symlink или не regular → `not_undoable`, отсутствие → `not_undoable`), SHA-256 открытого inode, затем `verify_parent_identity` (подмена → `blocked`). Для backup дополнительно проверяется родитель original. Изменённый созданный файл или повреждённый backup → `not_undoable`.

Применение undo, связь с SQLite Operation и Tauri command намеренно не реализованы.

## Тестовые точки и race-тесты

`file_service/hooks.rs` объявляет точки `BeforeTempCreate`, `BeforeRename`, `BeforeFinalVerify`, `BeforeCleanup { fileName }`, `PlanningParentOpened`, `UndoParentOpened`. В production-сборке `hooks::fire` — пустая `#[inline(always)]` функция, замыкание не вызывается. В `cfg(test)` хук thread-local и вызывается синхронно, поэтому подмена происходит строго между известными системными вызовами без sleep. Один тест дополнительно использует `std::sync::Barrier`: атакующий поток подменяет каталог, пока операция остановлена перед `rename`.

`race_tests.rs` (22 теста) проверяет подмену родителя на symlink до создания temp, перед rename, перед финальной проверкой, перед cleanup, во время planning и во время undo (created file и каталог backup); symlink в промежуточном компоненте, созданный после проверки destination; symlink leaf с тем же содержимым; regular file как промежуточный компонент; подмену source после открытия; FIFO как source; подмену самого vault root после открытия; symlink-компонент оригинала backup; появление destination перед rename (overwrite невозможен); сохранение `(2)`/`(3)` нумерации с кириллицей и отсутствие копии при `SameContent`. Каждый race-тест сравнивает побайтный снимок каталога `outside` до и после операции и проверяет, что в исходном каталоге не осталось temp/final файлов.

## Платформенные замечания

- Целевая платформа — macOS (APFS). `renameat_with(NOREPLACE)` использует `renameatx_np(RENAME_EXCL)` (macOS 10.12+); на Linux — `renameat2(RENAME_NOREPLACE)`.
- Если vault root переименован и на его место положен symlink уже после открытия, операции продолжаются в исходном inode корня, а не по новому пути (`vault_root_swapped_after_open_keeps_operations_in_original_inode`). Повторная проверка выбранного пользователем корня — задача слоя настроек при следующем открытии.
- Hardlink на regular file не является escape: запись идёт только в новые inode, существующие файлы не открываются на запись.

## Импорт во «Входящие» — этап 5

### Кто может назвать source

WebView не может попросить backend прочитать произвольный файл. `import_inbox_files` принимает только пути, которые backend сам получил: из системного диалога (`pick_import_files`, официальный `tauri-plugin-dialog` из Rust) или из native drag-and-drop окна (`WindowEvent::DragDrop`). Такие пути записываются в `IntakeGrants` (память процесса, TTL 30 минут, ≤ 4096 записей, только абсолютные regular files); путь вне списка → `blocked`. Повтор с тем же путём в пределах TTL разрешён — это нужно для идемпотентного повтора команды.

### `SourceFile::open_external`

Строже `SourceFile::new`:

1. абсолютный путь без `.`/`..`;
2. `lstat` каждого предка: symlink в родителе отклоняется (`blocked`), кроме системных алиасов macOS `/var`, `/tmp`, `/etc` → `/private/...` (иначе нельзя открыть ни один файл из `$TMPDIR`);
3. канонический родитель открывается покомпонентно от `/` через `openat(O_DIRECTORY | O_NOFOLLOW)`;
4. файл — `openat(O_NOFOLLOW | O_NONBLOCK)` + `fstat`: symlink, каталог, FIFO и устройства отклоняются;
5. `stat(path)` после открытия обязан указывать на тот же `(st_dev, st_ino)` — подмена между проверкой и открытием даёт `blocked`.

Остаточное окно: между `lstat` предков и `openat` канонического родителя локальный процесс может переставить каталоги; файл будет открыт из реального (не symlink) каталога, а шаг 5 отклонит несовпадение с указанным пользователем путём. Источник всё равно выбран самим пользователем.

### Порядок записи и компенсация

1. SHA-256, размер и копия читают один открытый inode; размер ≤ 4 ГБ.
2. Дубль по SHA-256 среди неразложенных записей → `duplicate` без копии (если файла записи на диске нет — он восстанавливается копированием; если файл на диске изменён — `conflict`, ничего не трогается).
3. Имя `Предметы/00 Входящие/<safe name>`; имя, занятое на диске (`plan_copy` → `NameConflict`) или в БД, заменяется на `<stem> (N).<ext>`. Файл с тем же содержимым на диске без записи (прерванный импорт) принимается без копии.
4. `atomic_copy_committed` (temp → fsync → `RENAME_NOREPLACE` → проверка inode и SHA-256 → fsync каталога) возвращает `CommittedCopy`.
5. Только затем — `INSERT INTO inbox_files`. Если вставка не удалась, `CommittedCopy::compensate` удаляет имя через `unlinkat(dir_fd)` **только** если оно указывает на созданный inode; чужой файл на том же имени не удаляется. Неудачная компенсация отражается в сообщении, а повторный импорт примет оставшийся файл без дубля.

### Безопасное имя

Разделители `/`, `\`, `:` и управляющие символы → `-`; bidi-override и zero-width символы удаляются (защита от визуальной подмены расширения); ведущие точки снимаются (скрытые файлы и префикс `.kontur-`); длина ≤ 200 байт UTF-8 с сохранением расширения до 16 байт; пустое имя → `Файл`.

### Действия ОС

`open_inbox_file`, `reveal_inbox_file`, `reveal_in_finder` строят абсолютный путь из канонического корня хранилища только после fd-relative проверки относительного пути (без symlink, конечный элемент существует). Исполняемые и скриптовые расширения (`.command`, `.sh`, `.app`, `.pkg`, `.webloc`, `.py` и др.) не открываются — только показ в Finder. Окно не имеет `dialog:*`, `opener:*` и `fs:*` permissions; доступны лишь `allow-<command>` «Контура» (41 команда после этапа 7).

## Экспорт ЦУ и watcher загрузок — этап 6

### Модель угроз

Дополнительно к локальному процессу из модели выше недоверенными считаются: содержимое папки загрузок (туда пишет браузер и любые сайты через загрузки) и любой архив, в том числе «экспорт LMS». Цели атаки: записать файл вне временного каталога (ZIP Slip, абсолютные пути, `\`, drive prefix, symlink-записи), исчерпать диск/память/время (zip-бомбы, overlapping-бомбы, рекурсивные архивы, ложные размеры), подменить файл между обнаружением и импортом, подсунуть ссылку на сторонний сайт под видом LMS, заставить «Контур» импортировать файл без ведома пользователя.

### Watcher

- Выключен по умолчанию; включается только явным действием пользователя; ничего не импортирует сам — только показывает кандидатов.
- Читает только верхний уровень папки загрузок через fd корня: `fdopendir` дубликата fd и `statat(AT_SYMLINK_NOFOLLOW)`; symlink, каталоги, FIFO и устройства отбрасываются, в подкаталоги не спускается. Каждый шаг заново проверяет политику корня (`DownloadsRoot::new`).
- Хэширует только стабилизированный файл (≤ 2 ГБ, учебные расширения), открытый `openat(O_NOFOLLOW | O_NONBLOCK)` в fd корня со сверкой inode.
- Кандидат хранит имя, inode, размер и mtime. При предпросмотре и импорте файл открывается заново по имени в fd корня; несовпадение любого из трёх (включая переиспользование inode после удаления) → `conflict`. Предпросмотр дополнительно сверяет SHA-256 со значением, вычисленным watcher.

### Архив

- Индекс читается позиционными чтениями (`pread`) из одного открытого inode; распаковка — только после явного подтверждения и только выбранных записей.
- Строгая проверка индекса (см. `lms/zip_safe.rs` и `IMPLEMENTATION_STATUS.md`, этап 6): одна EOCD в конце, без ZIP64/многотомности/префикса; лимиты числа записей, размера записи, суммы и коэффициента сжатия; безопасные имена; запрет symlink/специальных файлов, шифрования, неизвестных методов, совпадающих путей без учёта регистра, конфликтов файл/каталог, расхождения локального и центрального заголовков и перекрытия данных.
- Вложенные архивы не распаковываются никогда (по расширению — нельзя выбрать; по сигнатуре при распаковке — запись отклоняется).
- Распаковка не доверяет заголовку: поток ограничен `min(заявленный размер, лимит записи, остаток бюджета)`; превышение → `SizeMismatch`/лимит; после записи сверяются размер и CRC-32; SHA-256 считается по тем же байтам.

### Временный каталог

- `<app_data>/tmp` создаётся с правами 0700 (symlink на его месте отклоняется); для каждой операции — `tempfile::TempDir` с префиксом `.kontur-cu-`.
- `ScratchRoot` открывает каталог как directory fd; записи создаются как `NNNN/<безопасное имя>` через `mkdirat` и `openat(O_CREAT | O_EXCL | O_NOFOLLOW)` — структура архива на диске не воспроизводится, имя из архива проходит `safe_inbox_name`, перезапись невозможна.
- Распакованный файл открывается для импорта fd-relative (`SourceFile::open_in`) и импортируется прежним путём (SHA-256, `RENAME_NOREPLACE`, компенсация). Каталог удаляется явно перед записью итога и RAII при любой ошибке или panic; тесты проверяют, что после импорта (успешного, частичного и отклонённого) он пуст.

### Ссылки LMS

- Сохраняются и открываются только `https://my.centraluniversity.ru/...` (точный хост, без userinfo, порта, IP, пробелов и управляющих символов). WebView не может открыть произвольный URL: `open_course`/`open_assignment` принимают идентификатор предмета, ДЗ или файла, читают ссылку из SQLite и проверяют её повторно. Открытие — `tauri-plugin-opener` из Rust во внешнем браузере пользователя; окно не получает `opener:*`.
- Вход в LMS, cookies, сессии и отправка работ не реализуются и не автоматизируются.

## Извлечение текста — этап 7

### Модель угроз

Недоверенными считаются содержимое любого учебного файла (его могли подготовить третьи лица или сайт, с которого он скачан) и метаданные внутри него. Цели атаки: заставить «Контур» изменить или удалить оригинал, прочитать файл вне хранилища, исчерпать память/время (zip- и decompression-бомбы, «billion laughs», огромные листы), прочитать локальные файлы через XML-сущности (XXE) или relationships, выполнить макрос, формулу или встроенный объект, уронить приложение повреждённым файлом.

### Только чтение оригинала

- `file_service::read_vault_file` строит `VerifiedDestination::in_vault` (относительный `PersistentPath` без `..`, абсолютных путей и drive prefix) и открывает файл `SourceFile::open_in`: покомпонентный обход от fd хранилища с `O_NOFOLLOW`, `openat(O_RDONLY | O_NOFOLLOW | O_NONBLOCK)`, проверка regular file и identity родителя. Symlink в любом компоненте или на месте файла → `blocked`.
- Размер берётся `fstat` открытого fd; файл больше лимита (200 МБ) в память не читается — SHA-256 считается потоково, статус `too_large`. Иначе содержимое читается `pread` из того же inode, затем проверяется, что файл не вырос и `fstat` не изменился; SHA-256 считается по прочитанным байтам. Дальше разбор работает только с буфером в памяти.
- Файл никогда не открывается на запись, не переименовывается и не удаляется; рядом с ним ничего не создаётся (тест сверяет содержимое, mtime и состав каталога). SHA-256 «Входящих» сверяется с журналом импорта — изменённый вне «Контура» файл не анализируется (`conflict`).

### Office Open XML

- Пакет разбирается тем же строгим ZIP-парсером, что экспорт ЦУ, но из памяти (`ArchiveSource for [u8]`) и с лимитами извлечения: ≤ 10 000 записей, часть ≤ 128 МБ, сумма ≤ 512 МБ, коэффициент сжатия ≤ 200; обход пути, абсолютные пути, `\`, symlink/специальные файлы, шифрование, дубли без учёта регистра, расхождение заголовков и перекрытие данных отклоняют документ (`rejected`/`corrupt`). Распакованные части живут только в памяти и только XML.
- XML: `<!DOCTYPE>` в любой части → `rejected`; внешних и пользовательских сущностей не существует, раскрываются только `&amp; &lt; &gt; &quot; &apos;` и числовые ссылки; лимит событий на часть.
- Relationships: `TargetMode="External"` не открывается; цель нормализуется относительно каталога части, `..` за корень пакета, схемы URI (`file:`, `http:`), `\`, управляющие символы → цель отбрасывается. Чтение — только частей внутри уже проверенного индекса.
- `vbaProject.bin`, `embeddings/`, `activeX/`, `w:object`, OLE-объекты слайдов не читаются; формулы XLSX не вычисляются, внешние связи книги не обновляются.

### PDF, текст, изображения

- PDF: `lopdf` без default features (без rayon/chrono/изображений), лимит распаковки потока 64 МБ при загрузке и при извлечении текста, встроенные ограничения вложенности объектов. JavaScript, формы, вложения и ссылки PDF не используются.
- Текстовые файлы: лимит 32 МБ, двоичное содержимое (NUL) → `unsupported`, управляющие и bidi-символы удаляются. JSON ноутбука — `serde_json` с ограничением глубины рекурсии.
- Изображения: только чтение заголовка (`imagesize`), без декодирования пикселей.

### Изоляция разбора

Разбор — отдельный поток со стеком 32 МБ под `catch_unwind`; panic → `corrupt`. Кооперативный бюджет времени (60 с) проверяется между страницами/листами/слайдами и каждые 4096 XML-событий; сторожевой цикл вызывающей стороны каждые 50 мс проверяет отмену и срок и через 2 с после срока возвращает `timeout`, выставляя флаг остановки. Ограничение: поток, застрявший внутри одного вызова библиотеки, нельзя убить — он завершится на ближайшей проверке; отдельного процесса-песочницы нет.

### OCR

Выключен по умолчанию. Исполняемый файл ищется только в `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin`, `/usr/bin` (не через `PATH`), каноничный путь обязан остаться внутри этих префиксов и быть исполняемым. Запуск: очищенное окружение (`PATH=/usr/bin:/bin`), аргументы `stdin stdout -l <языки> --psm 3`, изображение через stdin (путь файла процессу не передаётся), stdout ограничен 4 МБ, stderr отброшен; по сроку или отмене процесс убивается.

## Процессы официальных CLI и файл ответа — этап 9

### Модель угроз

Недоверенными считаются: исполняемый файл на месте ожидаемого CLI (его мог подменить локальный процесс), окружение «Контура» (могут быть ключи), вывод CLI и ответ провайдера (могут содержать что угодно, в том числе команды или пути), файл ответа, выбранный пользователем (symlink, огромный, не текст), учебные материалы (prompt injection). Цели атаки: запустить чужой исполняемый файл, передать секреты в процесс или в журнал, дать CLI доступ к хранилищу, заставить «Контур» применить ответ без ведома пользователя, повесить приложение.

### Защита

- Поиск CLI — только фиксированные каталоги установки; канонический путь внутри разрешённых префиксов, обычный исполняемый файл, не общедоступный на запись, владелец — пользователь или root, каталог не общедоступен на запись. Запускается канонический путь (без повторного поиска по `PATH`).
- `Command` с argv (shell не используется), `env_clear()` + минимальное окружение (HOME, USER, LOGNAME, фиксированный PATH, LANG, NO_COLOR, TERM, TMPDIR в каталоге задания). Промт — через stdin, секретов и учебного текста в командной строке нет.
- Рабочий каталог — новый пустой каталог 0700 в данных приложения (`tempfile`), удаляется после запуска; хранилище Obsidian процессу не передаётся. Codex — `--sandbox read-only`, Claude — `--tools ""` и один ход.
- Своя группа процессов: тайм-аут и отмена убивают группу (SIGKILL). stdout ≤ 2 МБ, stderr ≤ 64 КБ; ожидание потоков чтения ограничено.
- Вывод входа (`codex login status`, `claude auth status`) не читается — только код выхода.
- Журнал, stderr и сообщения проходят редакцию (ключи, `Bearer`, значения секретных ключей, длинные токены, почта, домашний каталог и пользовательские пути); SQLite-триггеры дополнительно отклоняют пути в журнале.
- Ответ провайдера только разбирается (JSON-парсер, без выполнения), применяется через обычные проверки рабочего цикла и только после подтверждения пользователем. В текст передачи добавлено указание считать материалы данными, а не инструкциями (защита от prompt injection не абсолютна — поэтому подтверждение обязательно).
- Файл ответа: путь только из системного диалога backend; `open(O_RDONLY | O_NOFOLLOW | O_NONBLOCK)` + `fstat` (только обычный файл), размер ≤ 2 МБ (и при чтении), только UTF-8 (BOM снимается); сохраняется имя файла, путь — нет. Оригинал не изменяется.
- Официальное приложение/сайт: только фиксированные адреса (`/Applications/Claude.app`, `Codex.app`, `ChatGPT.app`, `https://claude.ai/new`, `https://chatgpt.com/`), открываются из Rust через `tauri-plugin-opener`; WebView не передаёт путь или URL.
- Окно не получает `shell:*`, `process:*`, `opener:*`, `dialog:*`, `fs:*` — только `allow-<command>` «Контура».

### Остаточные риски

- Между проверкой канонического пути и запуском локальный процесс с правами на запись в каталог установки (например, Homebrew-префикс пользователя) может подменить файл. Такой процесс и так может выполнить код от имени пользователя; «Контур» не повышает его возможности.
- Что CLI делает со своими учётными данными, сетью и историей, определяет сам CLI.

## Раскладка, заметки и undo — этап 10

- `preview_route` только открывает source/destination fd-relative и сравнивает SHA-256; каталог или файл не создаётся.
- `route_files` не overwrite-ит: одинаковое содержимое пропускается, конфликт имени получает свободное имя, новый файл публикуется атомарно. Ошибка БД вызывает inode-checked compensation.
- Markdown обновляется через temp-файл в том же открытом каталоге и atomic rename. Symlink/специальный файл вместо заметки отклоняется; заметка свыше 4 МиБ не переписывается.
- Undo сначала повторно проверяет SHA-256 и запреты submitted/already-undone, затем переименовывает каждый созданный inode во временное имя. До commit SQLite RAII возвращает исходное имя; после commit удаляется только тот же inode.
- Файл подтверждения отправки читается только по краткоживущему разрешению native picker; абсолютный source path не сохраняется. В receipt попадает только относительная копия внутри snapshot и её SHA-256.
- Автотесты создают vault/backup и учебные файлы исключительно внутри `TempDir`.
